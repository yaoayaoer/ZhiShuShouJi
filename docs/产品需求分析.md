# ZhiShuShouJi
让阅读留在纸上，让思考不止于纸上。一款专为纸质阅读打造的轻量化数字笔记工具，通过拍照摘录、感想记录与结构化检索，让纸上的知识被轻松记录、随时找回、持续积累。
# 一、项目背景：问题是什么

纸质阅读的内容记录存在两个连续断点：阅读当下，长段摘录依赖手抄或手机输入，操作耗时、打断阅读；阅读之后，划线与零散备忘录缺少书籍、页码和个人理解之间的关联，难以检索与复用。产品需要同时解决“低干扰采集”和“可追溯整理”，而不是再做一款通用笔记软件。

现有替代方式：纸上划线成本低但跨书检索困难；手机备忘录录入方便但缺少书籍上下文；通用知识管理工具组织能力强，但纸书现场录入链路通常较长。以上属于产品分析假设，需通过访谈和任务测试验证，不能直接作为市场事实。

产品定位：面向有纸质阅读与回顾需求的人群，以“书籍—摘录—感想—页码”为最小内容单元，完成快速采集、结构化保存与再次找回。非目标：电子书阅读器、阅读社区、全能知识库。

# 二、需求分析：用户、场景与任务

| 目标用户              | 高频任务                       | 核心障碍             | 优先价值           |
| --------------------- | ------------------------------ | -------------------- | ------------------ |
| 稳定阅读的学生/研究生 | 摘录资料、写读书笔记、复习引用 | 手输耗时，出处易丢失 | 拍照摘录与书页关联 |
| 教师/研究人员         | 按主题回找书中论述             | 多书笔记分散         | 关键词、书籍检索   |
| 阅读输出创作者        | 积累素材并附加观点             | 原文与感想混杂       | 摘录/感想分离保存  |

核心任务链：选书/建书 → 拍照或手动录入 → 校对摘录 → 补充感想与页码 → 保存 → 按书名/关键词找回。产品成功的判断应覆盖完整任务链，而非仅看OCR识别成功率。

# 三、需求拆解：真实需求与功能映射

| 用户需求（Why）    | 功能方案（What）         | 必要约束                                 |
| ------------------ | ------------------------ | ---------------------------------------- |
| 阅读时快速保存内容 | 快捷新建、手动输入、OCR  | 识别文本可选择、可编辑；失败可手输       |
| 笔记有明确出处     | 书籍归属、页码、原图可选 | 每条笔记必属一本书；摘录和感想至少有一项 |
| 记录自己的理解     | 独立感想字段             | 不强制填写感想；允许只有感想的笔记       |
| 日后能找回         | 按书聚合、全文关键词搜索 | 搜索覆盖书名、作者、摘录和感想           |
| 内容安全可信       | 本地持久化、删除确认     | 明确删除影响；避免无提示丢失             |

# 四、优先级决策：标准与结论

决策原则：先保证核心闭环，再解决最明显的现场输入摩擦，最后做体验增强。使用简化RICE/价值—成本判断：用户覆盖、问题强度、对主链路的必要性、实现成本与依赖风险。当前缺少真实用户规模及开发工时，因此不编造精确评分；以下为基于依赖关系的初步排序。

| 优先级        | 功能                                                         | 决策依据                                             | 版本归属    |
| ------------- | ------------------------------------------------------------ | ---------------------------------------------------- | ----------- |
| P0 必须       | 书籍管理、笔记CRUD、手动输入、SQLite持久化、按书查看、基础关键词搜索 | 没有这些无法完成保存—找回闭环；OCR也依赖笔记数据结构 | MVP / V0.1  |
| P1 核心差异化 | OCR拍照、裁剪/校对、失败回退、页码与原图关联                 | 直接减少长摘录输入负担；是纸书场景核心价值           | V1.0 必须   |
| P1 完善       | 标签及筛选、草稿保护、关键错误提示                           | 提升回找与稳定性；标签可在核心闭环稳定后开发         | V1.0 视工期 |
| P2 延后       | 语音转文字、数据导出、收藏置顶、深色模式                     | 有体验价值，但不阻断主要任务                         | V1.1+       |
| P3 暂不做     | 账号/云同步、社区、AI摘要、RAG问答、Agent                    | 开发与运营复杂度高，尚无必要性验证                   | 后续探索    |

特别说明：OCR虽然排在基础CRUD之后开发，但属于正式V1.0验收必需项；语音输入从V1.0必需范围移出，避免版本范围自相矛盾。若目标是微信小程序而非原PRD的Android/iOS原生App，本地存储方案、相机权限、OCR接入和数据持久性需要重新做技术评估，不能直接照搬SQLite设计。

# 五、MVP与V1.0交付边界

V0.1（技术闭环）：创建书籍→新建手动笔记→保存→按书浏览→关键词搜索→编辑/删除。可不接OCR，重点验证信息结构与数据可靠性。

V1.0（可用产品）：在V0.1上增加拍照OCR、识别结果校对、页码记录、错误处理与基础隐私说明；标签功能按资源作为次优先项。V1.0不以AI、云同步和社交功能作为交付条件。

# 六、验收指标与验证方案

| 维度       | 建议验收口径（目标值待实测调整）                        | 验证方式           |
| ---------- | ------------------------------------------------------- | ------------------ |
| 任务完成   | 新建书籍、手动笔记、OCR笔记、检索回看四条主链路均可完成 | 任务测试逐条核验   |
| 录入效率   | 记录从打开入口到成功保存的耗时；比较手输与OCR           | 同一段文字对照测试 |
| OCR可用性  | 识别结果可编辑；无权限、空结果、失败均有回退            | 正常/异常用例测试  |
| 数据可靠性 | 重启后数据仍在；删除有二次确认；异常退出尽量保留草稿    | 持久化与异常测试   |
| 检索有效性 | 已保存的书名、摘录、感想关键词能命中对应记录            | 构造测试集核验     |

验证优先级：先访谈5—8位真实纸书读者，观察现有记录流程；再让5位目标用户执行摘录—回找任务，记录完成率、耗时、错误与放弃原因。样本仅用于发现问题，不代表市场统计结论。

# 七、主要风险与取舍

| 风险                | 影响                   | 应对决策                                |
| ------------------- | ---------------------- | --------------------------------------- |
| OCR误识别、复杂排版 | 摘录错误与额外校对成本 | 必须允许裁剪、修改和手动回退            |
| 过多必填字段        | 阅读过程被打断         | 仅强制书籍归属和至少一项正文；页码可选  |
| 本地数据丢失        | 用户长期内容损失       | 持久化测试、删除确认；尽早规划导出/备份 |
| 平台定义不一致      | 架构返工               | 开发前确定微信小程序还是原生App         |
| 提前引入AI能力      | 成本与范围失控         | 先验证记录和回找需求，再评估RAG价值     |

# 八、当前需要拍板的决策

决策1：确定首发平台（微信小程序或原生移动端），再定存储与OCR技术路线。决策2：正式V1.0必须包含OCR，但不包含语音转文字。决策3：优先保证“书籍—笔记—检索”的稳定关系，标签可根据工期调整。决策4：上线前以真实任务测试验证“是否比备忘录更快、更容易回找”，而不是用功能数量衡量成功。

结论：纸书手记的产品价值不在于记录功能本身，而在于降低纸书摘录的中断成本，并保留可回溯的阅读语境。优先级应沿着“能保存 → 容易录入 → 能找回 → 再扩展”推进。
